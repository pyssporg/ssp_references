# IMP-007: ADR Template and Layer Boundary Clarification (KM-005)

**ID:** IMP-007
**Status:** proposed
**Theme:** Documentation Tooling — Technical Decisions Layer (KM-005)

**Evidence:**
- **Finding 2 (critical review):** ADR-001 (Three-Stage Pipeline) and ADR-002 (Fixture Hierarchy) record decisions about the system *structure* — the very domain that `docs/02-system-architecture/architecture.md` describes as stable boundaries. KM-005 defines Technical Decisions as "bridging architecture to build details," but these ADRs explain *why the architecture is the way it is* rather than bridging to build details. This creates a grey zone between the System Architecture and Technical Decisions layers and a maintenance risk (both architecture.md and the ADRs describe the pipeline structure).
- **Finding 4 (critical review):** The ADR template at `.opencode/templates/others/adr-template.md` has a "Traceability" field but no awareness of KM-005 layer separation, no `Layer:` field, and no guidance about which layer an ADR occupies.
- **Finding 6 (critical review):** The template's traceability instruction says "Link or reference the intent, product commitment, architecture, implementation, and verification artifacts this ADR satisfies." This encourages linking *downward* (from ADR to implementation), which KM-005 explicitly says higher layers should not do.
- The README at `docs/03-technical-decisions/README.md` describes ADRs as "documenting significant architectural choices" but does not distinguish between product decisions, architecture decisions, and technical decisions. The term "architectural choices" conflates the layers.
- The design decisions log (`design-decisions-log.md`) does not identify its layer either.

**Current pain or risk:**
1. New ADR authors have no guidance about which KM-005 layer their ADR belongs to, so they will likely continue mixing layers in `03-technical-decisions/`.
2. The template encourages downward trace links (ADR → implementation), which contradicts KM-005's "higher layers do not link down into implementation details" rule.
3. ADR-001 and ADR-002 duplicate architecture doc content, creating a stale-reference risk (KM-007) if one is updated without the other.
4. The README.md's "backward trace" section is accurate but incomplete — it doesn't explain how ADRs relate to the KM-005 layer chain.

**Proposed improvement:**
1. Update the ADR template (`.opencode/templates/others/adr-template.md`) to:
   - Add a `**Layer:**` field (values: `Product Decision`, `Architecture Decision`, `Technical Decision`) that forces the author to identify which KM-005 layer the ADR belongs to.
   - Replace the "Traceability" instruction with a strict backward-only trace rule: "Reference the intent, product commitment, or architecture artifact this ADR satisfies. Do not link down to implementation or verification artifacts."
   - Add a comment or footnote explaining the KM-005 layer chain and reminding authors that implementation details belong in the design decisions log or FIXTURE.md, not in an ADR.

2. Update `docs/03-technical-decisions/README.md` to:
   - Clarify that ADRs in this directory are Technical Decisions per KM-005, and that ADR-001 and ADR-002 document the rationale behind architectural choices (rather than bridging to build details, which is noted as a grey zone).
   - Add a "Layer Map" section showing how the ADRs relate to KM-005 layers.
   - Explicitly state that product-level decisions should go in `docs/01-product-decisions/` (if IMP-006 is implemented — use a forked instruction if IMP-006 is not yet done).
   - Add a maintenance note: "When updating an ADR that describes a system structure also documented in architecture.md, verify both documents stay consistent."

3. Add a `**Layer:**` front-matter line to each existing ADR (ADR-001: "Architecture Decision", ADR-002: "Architecture Decision", ADR-003: "Technical Decision") so the new field is populated from the start. Do not change any ADR content beyond adding the Layer field.

4. Do **not** restructure ADR-001 or ADR-002 — the scope of this ticket is to clarify the boundary and reduce duplication risk, not to rewrite or merge the ADRs into architecture.md. A future IMP can decide whether to absorb them into the architecture doc.

**Expected benefit:**
- New ADRs follow a consistent layer-aware template with backward-only trace links.
- The ADR README makes layer affiliation explicit, reducing confusion for future agents and contributors.
- The stale-reference risk between ADR-001/002 and architecture.md is documented and mitigated.
- KM-005 reviews gain a verifiable check: "Does the ADR template enforce layer identification and backward-only traces?"

**Risk and blast radius:**
- **Risk:** Low. Touches one template file, one README, and adds one front-matter line to three existing ADRs. No content changes to ADRs or architecture.md.
- **Risk of over-specification:** The `Layer:` field must allow `Architecture Decision` as a value even though it's not in KM-005's strict chain, because ADR-001/002 genuinely document architectural choices. The template documentation should explain that "Architecture Decision" captures decisions *about* the architecture that sit between System Architecture and Technical Decisions in practice.
- **Blast radius:** 1 template edit, 1 README edit, 3 ADR edits (one line each). No code changes, no architecture doc changes, no intent doc changes.

**Prerequisites:** None, but if IMP-006 is implemented first, the README update should reference `docs/01-product-decisions/`. If IMP-006 is not yet done, the README should say "product-level decisions currently live in intent.md's Product Commitments section."

**Suggested priority:** High (low blast radius, directly addresses KM-005 layer confusion in the primary decision-recording mechanism).
