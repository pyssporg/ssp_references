# IMP-002: System Architecture Document

**ID:** IMP-002
**Status:** proposed
**Theme:** Architecture Documentation — Architecture Layer (KM-005)

**Evidence:**
- No explicit architecture document exists. Architecture is expressed implicitly through:
  - `README.md` layout (L11-41) — directory hierarchy, not architectural intent.
  - `AGENTS.md` — operational guidelines, not architecture.
  - `docs/03-technical-decisions/design-decisions-log.md` — current design decisions as bullet points.
  - `.opencode/agents/` — agent definitions encode workflow roles but are not an architecture document.
- KM-005 requires a "System Architecture" layer that describes "stable guarantees and boundaries" — this is completely missing.
- KM-002 (architecture constraints) exists as a rule but has no architecture document to reference during review.

**Current pain or risk:**
Architecture is reverse-engineered from code layout and agent instructions. Agents and contributors must guess at the stable boundaries (e.g., what belongs in `build.py` vs `run_simulations.py`, why certain models are in `models/ssp/` vs `models/fmu/`). Without an explicit architecture, KM-002 reviews have nothing to check against except implicit patterns.

**Proposed improvement:**
Create `docs/architecture.md` describing:
1. The three-stage pipeline: Build → Simulate → Compare, with stable interface contracts between stages.
2. The fixture hierarchy: FMU building blocks → simple reference SSPs → signal-propagation fixtures → composite SSPs.
3. Key architectural boundaries: what each entry point (`build_models.py`, `run_simulations.py`, `run_comparisons.py`) owns.
4. Data flow: how models become SSPs, how SSPs become simulation results, how results become comparisons.
5. The runtime contract: `simulation_registry.json` → `setup.json` → simulation artifacts → comparison artifacts.
6. Explicit forbidden shortcuts: e.g., "build.py does not run simulations", "experiments.xml is not the runtime contract."

**Expected benefit:**
- Every future task can reference a stable architecture document during planning and review.
- KM-002 reviews gain a concrete document to check against.
- New contributors understand the system boundaries without reading every agent definition.
- Reduces the divergence pain by making the intended architecture visible.

**Risk and blast radius:**
- **Risk:** Low-medium. New file in `docs/`. Must be maintained as the architecture evolves, but the documented boundaries (three-stage pipeline, artifact hierarchy) are stable.
- **Risk of duplication:** Must not duplicate `docs/co_simulation_test_strategy.md` (test strategy) or `strategy`) or `docs/co_simulation_fixture_mapping.md` (fixture mapping). KM-005 layer separation must be preserved — architecture doc describes *stable guarantees and boundaries*, not testing strategy or fixture details.
- **Blast radius:** Low. One new file. May update `AGENTS.md` "Repository Focus" or documentation guidelines to reference it, but that is optional and deferred.

**Suggested priority:** High

**Task contract seed:**
Create `docs/architecture.md` covering: (1) The three-stage pipeline (Build → Simulate → Compare) with explicit interface contracts — what each stage produces and consumes, (2) Fixture hierarchy — how FMU building blocks, simple reference SSPs, signal-propagation fixtures, and composite SSPs relate, (3) Key architectural boundaries — what each entry point in `scripts/` is responsible for and forbidden from doing, (4) Data flow diagram (text-based) showing the path from model source to comparison artifact, (5) Runtime contract — how `simulation_registry.json`, `setup.json`, simulation artifacts, and comparison artifacts connect. Do not reference specific model names, tolerance values, or pass/fail criteria (those belong in strategy docs). Do not duplicate `docs/co_simulation_test_strategy.md` content.

**Notes:** IMP-001 (purpose document) should be created first so the architecture doc can trace backward to it. The architecture doc should stay high-level about pipeline boundaries and avoid drifting into fixture-specific notes.
