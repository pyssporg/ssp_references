# IMP-001: Explicit Overarching Purpose Document (System Intent & Commitments)

**ID:** IMP-001
**Status:** proposed
**Theme:** Purpose Documentation — Intent Layer (KM-005)

**Evidence:**
- README.md L1-9 states *what* the repo is ("Curated SSP model fixtures plus the scripts...") without stating *why* it exists or what commitments it makes.
- `docs/co_simulation_test_strategy.md` L5-8 contains the closest purpose statement ("validate a co-simulation engine..."), but it lives in a strategy doc and is not a top-level declaration.
- KM-005 defines an Intent → Architecture → Decisions → Implementation chain, but Intent is the missing first link.
- AGENTS.md "Repository Focus" (L14-18) is a short restatement of the README, not a binding purpose.

**Current pain or risk:**
Without an explicit purpose, contributors and agents must infer the north star from the directory layout and existing code. This causes divergent interpretations of what belongs in the repository and what is out of scope. The pain statement in PROMPT.md names this directly: "lack of an explicit overarching purpose, architecture and traceability of design decisions are causing divergence within the implementation."

**Proposed improvement:**
Create a lightweight `docs/intent.md` that:
1. States the primary purpose of the repository in terms of the problem it solves.
2. Lists explicit product commitments (e.g., "SSP models must be reproducible", "Engine comparison results are the primary quality gate").
3. Defines explicit non-goals / out-of-scope boundaries.
4. Sits at the Intent layer of KM-005 — it does not describe architecture, decisions, or implementation details.

**Expected benefit:**
- All future design decisions trace back to a stable north star.
- New contributors and agents can quickly determine whether a proposed change is in-scope.
- Reduces divergence by constraining interpretation at the top of the documentation chain.

**Risk and blast radius:**
- **Risk:** Low. A new file in `docs/` — no code, no existing file modifications. KM-004 (parallel structures) is respected because `docs/` is the existing canonical home for strategy notes.
- **Risk:** If the purpose statement becomes too broad or too narrow, it could constrain useful work. Mitigation: keep it concise and reviewable as part of the improvement workflow.
- **Blast radius:** Low. Only one new file. No changes to directory layout, agent definitions, or workflow scripts.

**Suggested priority:** High

**Task contract seed:**
Create `docs/intent.md` with three sections: (1) Repository Purpose — a single paragraph stating why this collection of SSP fixtures and scripts exists, (2) Product Commitments — 3-5 bullet points listing what the repository promises (e.g., fixtures are reproducible, comparison results are the quality gate, models follow a documented build contract), (3) Non-Goals — 2-3 bullet points stating what the repository does not attempt (e.g., validating engine correctness in the absolute sense). Do not reference architecture decisions, specific model names, or implementation details. Do not modify any other file. Verify that the document is self-contained, does not link into lower-layer docs, and can be read as a standalone north star.

**Notes:** This candidate is the prerequisite for all other traceability candidates. Without an explicit purpose, architecture and decision documents lack a reference point.
