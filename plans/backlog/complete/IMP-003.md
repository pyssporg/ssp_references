# IMP-003: Architecture Decision Record (ADR) Mechanism

**ID:** IMP-003
**Status:** proposed
**Theme:** Design Decision Traceability — Technical Decisions Layer (KM-005)

**Evidence:**
- `todo.md` L40-49 captures 4 current decisions as bullet points with no rationale, no alternatives considered, and no consequence notes.
- `.opencode/known-mistakes.md` KM-005 defines a documentation chain that includes "Technical Decisions" as a dedicated layer, but no ADR mechanism exists to populate it.
- FIXTURE.md files capture fixture-level notes but not the *design decisions* behind fixture structure, packaging choices, or build patterns.
- Commit messages contain some rationale but are not auditable without reading `git log`.
- No ADR directory, template, or convention exists in the repository.
- `docs/03-decisions/design-decisions-log.md` — captures implementation-level design decisions without requiring a full ADR.
- The pain statement ("lack of... traceability of design decisions are causing divergence") directly names this gap.

**Current pain or risk:**
When a future task encounters a design choice (e.g., "why do some signal-propagation fixtures use external SSV files while others inline parameters?", "why was the three-backend design chosen?"), the answer requires reading git history or reverse-engineering from code patterns. This causes re-litigation of settled decisions and divergent implementations that don't respect the original rationale.

**Proposed improvement:**
Establish an ADR directory (`docs/03-decisions/`) with:
1. A minimal ADR template (Title, Context, Decision, Consequences).
2. The first 3-5 ADRs recording already-settled design decisions (e.g., "Three-stage Build-Simulate-Compare pipeline", "Signal-propagation fixtures use deterministic algebraic building blocks", "Simulation settings belong to runtime registry, not experiments.xml").
3. An AGENTS.md convention update directing agents to create ADRs for significant architectural decisions.

**Expected benefit:**
- Every significant design decision has a stable, auditable record.
- Future tasks can consult ADRs to understand tradeoffs without repeating analysis.
- KM-005's "Technical Decisions" layer becomes populated.
- Reduces divergence by making decision rationale visible instead of implicit.

**Risk and blast radius:**
- **Risk:** Medium. Requires creating a new directory, a template, and a maintenance convention. The ADRs must be kept reasonably up-to-date or they become misleading.
- **Risk of overhead creep:** Not every decision needs an ADR. The template and convention must be clear about what warrants one (architectural decisions, interface contracts, significant tradeoffs) vs what does not (trivial variable naming, one-off fix choices).
- **Blast radius:** New directory `docs/03-decisions/`, new template in `.opencode/templates/others/adr-template.md`, update to `AGENTS.md` documentation guidelines. Does not modify existing code or docs.

**Suggested priority:** Medium (depends on IMP-001 and IMP-002 existing first)

**Task contract seed:**
(1) Create `.opencode/templates/others/adr-template.md` with fields: Title, Status (proposed/accepted/superseded/rejected), Context (why the decision was needed), Options Considered (2-3 alternatives), Decision (the chosen approach), Consequences (tradeoffs, constraints created). (2) Create `docs/03-decisions/README.md` explaining the ADR mechanism and linking the template. (3) Create the initial ADRs: ADR-001 (Three-stage pipeline architecture — Build/Simulate/Compare as separate stages with manifest interfaces), ADR-002 (Fixture hierarchy — FMU building blocks as base units, SSP fixtures layered on top), ADR-003 (Runtime configuration belongs to the simulation registry, not experiments.xml). (4) Update AGENTS.md documentation guidelines to note the ADR mechanism and when to create new ADRs. Do not modify any source code, build scripts, or FIXTURE.md files.

**Notes:** This candidate depends on IMP-001 and IMP-002 for purpose and architecture context. The ADR mechanism should be lightweight — a few template fields and a directory convention, not a full governance process.
