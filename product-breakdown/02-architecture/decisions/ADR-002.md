# ADR-002: Fixture Hierarchy

**Status:** Accepted
**Layer:** architecture-decision

---

## Context

The repository needed a consistent way to organize its growing collection of
SSP fixtures. Without an explicit hierarchy, new fixtures could be added
ad-hoc with inconsistent structure, and it would be unclear which class of
fixture serves which testing purpose.

## Options Considered

1. **Flat fixture collection** — All SSPs treated as equal, distinguished only
   by metadata tags.
2. **Two-level hierarchy** — Simple reference models at one level, everything
   else at another.
3. **Four-class hierarchy** — FMU building blocks, simple reference SSPs,
   deterministic signal-propagation fixtures, and composite SSPs.

## Decision

Adopt a four-class fixture hierarchy:

1. **FMU building blocks** (`models/fmu/`) — Reusable signal-processing FMUs
   (sources, gains, combiners) that are the leaf dependencies.
2. **Simple reference SSPs** (`models/ssp/`) — Single-FMU SSPs serving as basic
   behavioral checks.
3. **Deterministic signal-propagation fixtures** (`models/ssp/`) — SSPs
   composed from two or more FMU building blocks to exercise specific
   propagation scenarios.
4. **Composite SSPs** (`models/ssp/`) — Multi-component SSPs exercising
   realistic coupling behavior.

## Consequences

- New fixtures have a clear architectural home and purpose class.
- The hierarchy maps directly to comparison tolerance expectations (tightest
  for propagation fixtures, moderate for simple references, broadest for
  composites).
- Adding a new fixture class would require an explicit decision and an ADR
  update.
- The four classes are not always mutually exclusive (a composite could contain
  propagation fixtures), but the hierarchy captures the primary intent.
