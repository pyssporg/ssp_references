# IMP-011: System Simulation Use-Case Coverage Analysis and Gap Tracking

## Status

Proposed

## Layer

Evolution (06-evolution) — cross-cutting coverage analysis spanning
Verification (04-verification), Implementation (03-implementation, fixtures),
and Architecture (02-architecture, fixture hierarchy).

## Theme

Define a taxonomy of system simulation use-cases that the fixture suite should
cover, map existing tests against it, identify coverage gaps, and establish a
framework for prioritizing new fixture and test work based on functional
coverage rather than low-level programmatic verification.

## Evidence

A comprehensive analysis of the 11 existing test functions in
`tests/test_workflow.py` reveals:

### Tests performing low-level function verification (engine-repo scope)

Two existing tests verify implementation details that belong in the simulation
engine projects, not this repository:

1. **`test_reference_csvs_are_not_inverted`** — checks specific numeric cell
   values in reference CSV files (BouncingBall, Dahlquist, Stair, VanDerPol).
   This is value-level correctness verification of reference data.

2. **`test_modelica_block_fmus_expose_dependency_metadata`** — parses FMU
   `modelDescription.xml` and checks `dependencies` attribute strings on
   Modelica Gain and Add blocks. This is FMU metadata structure verification.

These tests should be transferred to the respective engine repositories and
removed from this repository's test suite.

## Current Pain Or Risk

- The test suite extensively covers pipeline mechanics (registry, manifests,
  comparison infrastructure) but never validates that the pipeline actually
  simulates the intended system behavior.
- 10 out of 16 identified use-cases have zero test coverage — the core purpose
  of the fixture suite (exercising SSP model functionality) is untested.
- Without a shared coverage taxonomy, new fixture and test work is prioritized
  ad-hoc rather than against a gap map.
- Low-level function verification tests (reference CSV values, FMU metadata)
  create maintenance burden in this repo without providing system simulation
  coverage value.

## Proposed Improvement

1. **Adopt the use-case taxonomy** (UC-1 through UC-16) as the canonical
   coverage framework for the fixture suite. Version it in this artifact.

2. **For each uncovered use-case**, produce a brief assessment:
   - Which existing fixtures could cover it (if any)
   - Whether new fixtures are needed
   - Priority for adding test coverage

3. **Establish a coverage review cadence**: each improvement cycle evaluates
   the matrix and updates it with newly-closed gaps.

4. **Flag engine-level verification tests** for transfer: the two tests
   identified above should be moved to the simulation engine repositories and
   removed from `tests/test_workflow.py`.

5. **Use the matrix as a prioritization tool**: coverage gaps directly inform
   the priority of fixture-add candidates (IMP-009, IMP-010), pipeline
   integration tests (IMP-013), and signal propagation coverage tests
   (IMP-017, new).

## Expected Benefit

- Clear shared understanding of what the test suite actually covers vs. what it
  should cover.
- Data-driven prioritization of new fixture and test work.
- Removal of engine-level verification burden from this repo.
- Measurable progress: coverage gaps are tracked and closed over time.

## Risk And Blast Radius

Low. Artifact-only change — no code modifications. The taxonomy and matrix are
documentary and do not alter any existing tests, fixtures, or pipeline code.
Risk is limited to:
- Taxonomy may need refinement as new fixture types are added.
- Matrix must be kept in sync with the actual test suite (requires periodic
  review, recommended per improvement cycle).

## Suggested Priority

High — establishes the framework that all other coverage-improvement candidates
depend on.

## Task Contract Seed

1. **Finalize taxonomy**: Review UC-1 through UC-16 with stakeholders. Add/
   remove/rename use-cases as needed. Publish in this artifact.

2. **Publish gap assessment**: For each uncovered or partially-covered use-case,
   write a brief gap assessment covering:
   - Existing fixtures that partially exercise the use-case
   - New fixtures needed (if any)
   - Minimum test scope to close the gap
   - Dependencies on other candidates (IMP-009, IMP-010, IMP-013, etc.)

3. **Flag engine-level tests for transfer**: File issues/PRs to move
   `test_reference_csvs_are_not_inverted` and
   `test_modelica_block_fmus_expose_dependency_metadata` to the appropriate
   engine repos. Once confirmed, remove from this repo's test suite.

4. **Create IMP-017 candidate** (or fold into this one): "Signal propagation
   coverage tests" — tests that verify the pipeline correctly handles
   signal-propagation fixtures without performing low-level algebraic checks.

5. **Update `co_simulation_test_strategy.md`** to reference the use-case
   taxonomy as the primary coverage lens.

## Out Of Scope

- Adding low-level programmatic algebraic verification tests (e.g., loading
  result CSVs and asserting `add.y = step_a.y + step_b.y`) — that is engine
  verification, not system simulation coverage.
- Modifying any fixture build scripts or checked-in resources.
- Changing the comparison pipeline, registry schema, or any pipeline code.
- Implementing the tests for individual use-cases (that is the scope of IMP-017
  and other implementation-phase candidates).

## Traceability

- Intent: Systematic coverage of system simulation use-cases across the fixture
  suite.
- Product: PD-002 (fixture hierarchy) — the taxonomy maps directly to fixture
  classes.
- Verification: This artifact IS the coverage analysis and gap tracking
  framework.
- Evolution: The matrix should be updated as new gaps are closed in subsequent
  improvement cycles.

## Notes

This candidate reframes the original IMP-011 scope. The previous scope
("programmatic algebraic signal relationship verification") proposed adding
low-level assertion tests like `assert add.y == step_a.y + step_b.y` to this
repository. Per stakeholder feedback, that verification belongs in the
simulation engine projects. This revised scope focuses on use-case coverage
analysis — what system simulation functionality does the suite exercise, and
where are the gaps?
